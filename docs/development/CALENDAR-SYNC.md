# Direct Google and Outlook interview sync

Feature 35 connects one primary Google calendar and one default Outlook calendar per JobPilot account. Sync is explicit: each saved interview round has **Send to Google/Outlook**, **Import from Google/Outlook**, and **Unlink** controls. It does not watch calendar changes or run a background calendar dispatcher. Static `.ics` downloads remain available without OAuth.

Sending creates or updates a JobPilot-linked single event without attendees. Newly created events use Google private visibility or Outlook private sensitivity; later updates preserve provider privacy settings. Only the round name, start/end time and meeting link/venue leave the application. The user confirms that those fields may be visible through their calendar sharing settings. Preparation notes, outcomes, resumes and application status remain in JobPilot. Attendee-bearing and recurring provider events cannot be updated, so sync does not issue meeting invitations. Google writes suppress attendee updates. Cancelled JobPilot rounds remain as free/transparent events with `[Cancelled]` in their titles; they are not deleted externally.

Import replaces scheduling fields after explicit confirmation, preserves the existing IANA display timezone, and leaves notes/outcomes unchanged. Later edits to other round fields preserve the stored instant (including seconds and the chosen instant in a repeated DST hour) when its clock time and timezone are unchanged. A deleted/cancelled provider event marks the round cancelled. All-day, recurring, invalid-time or oversized provider data is rejected. Existing private notes are never taken from calendar event bodies.

## Activation

1. Migration `supabase/migrations/20261005161114_calendar_connections.sql` was deployed to production on 2026-10-05 after user approval under the repository migration policy. It adds owner-readable connection metadata and event links, server-only encrypted token storage, per-calendar leases, and atomic credential/import functions. Existing interview rows receive a composite uniqueness constraint for owner-safe event links.
2. Configure a random 32-byte base64 `CALENDAR_ENCRYPTION_KEY` in the server deployment (for example, generate once with `openssl rand -base64 32`). Back it up securely. Never print/store it in chat, client bundles or Git. Loss/rotation requires reconnecting existing calendars; ciphertext cannot be restored without the original key.
3. Use dedicated calendar OAuth web applications; existing Supabase Google sign-in remains separate:
   - Google: enable Calendar API, configure consent/test users and a web client, and set `GOOGLE_CALENDAR_CLIENT_ID` / `GOOGLE_CALENDAR_CLIENT_SECRET`. Requested scope: `https://www.googleapis.com/auth/calendar.events`, with offline access. Public rollout may require Google consent verification. [Official web-server OAuth guide](https://developers.google.com/identity/protocols/oauth2/web-server).
   - Outlook: register a confidential **Web** client with support for the intended work/school and personal Microsoft accounts. Set `OUTLOOK_CALENDAR_CLIENT_ID` / `OUTLOOK_CALENDAR_CLIENT_SECRET`. Delegated scopes: `offline_access Calendars.ReadWrite`; app-only permissions are not used. Organizational policy or missing mailbox licenses may block access. [Microsoft authorization-code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).
   - Register the exact canonical HTTPS callback `https://<NEXT_PUBLIC_SITE_URL host>/api/calendars/callback` in both web clients. The app requires an explicit canonical HTTPS origin, existing Supabase server credentials, and these provider-specific settings before enabling Connect. Secrets stay server-side.
4. Sign in, connect from Profile in the same browser and finish provider consent. OAuth state is encrypted, expires after ten minutes, and binds the current JobPilot account and PKCE verifier. The callback clears its HttpOnly, Secure, SameSite=Lax cookie and stores credentials atomically. Existing connections must be disconnected before switching accounts.
5. With disposable calendar accounts, verify each provider’s create/update/import, refresh, conflict/412 response, cancellation, unlink/recreate and disconnect behavior. The implementation has only used provider mocks; no real calendar events were created or edited during validation.

## Correctness, privacy and limits

- OAuth tokens use AES-256-GCM with an owner/connection/token-purpose binding. Authenticated clients cannot read token rows or lease tokens, write connection metadata, forge event links, or execute sync/storage/import RPCs. Connection metadata and event links are included in account JSON export; OAuth credentials are deliberately excluded.
- Sync leases serialize operations per calendar for three minutes; the route is bounded to 120 seconds. Concurrent sync requests return a retryable conflict. A deleting account cannot connect, claim sync or import. All connection/token/link rows cascade on account deletion.
- Sending compares the stored provider ETag with the latest event before writing and uses `If-Match`. Changed events return a conflict, requiring an explicit import before sending local edits. Local imports update only the expected interview version and advance the event link in one database transaction, so stale/invalid imports cannot partially overwrite a round. [Google conditional updates](https://developers.google.com/calendar/api/guides/version-resources), [Graph precondition errors](https://learn.microsoft.com/en-us/graph/errors). Actual Outlook conditional-write behavior remains a real-provider release check.
- A pending event link is stored before creating its provider event. Google uses its UUID-derived event ID; Outlook uses a stable `transactionId` to recover creation retries. Provider timeouts can still be ambiguous; reload before retrying. [Graph event transaction IDs](https://learn.microsoft.com/en-us/graph/api/resources/event?view=graph-rest-1.0), [Google event creation](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert).
- A removed/cancelled provider event is not silently recreated. Import its cancellation, or explicitly unlink and send again. Unlink/disconnect retains provider-owned events. Sending after unlink creates a new event and can duplicate an existing retained event; the confirmation states this.
- Disconnect/account deletion removes stored credentials and stops future app sync. External calendar events and provider consent remain; revoke app access through Google/Microsoft account permissions as needed. One provider request already in flight can still finish after disconnect/deletion.
- Each round syncs independently and only to the default calendar. One linked event per round/provider is supported. No arbitrary calendar import, calendar selection, attendee management, recurrence conversion, automatic conflict merge, push webhooks or background reconciliation is implemented. Add those when explicit user workflows require them.
